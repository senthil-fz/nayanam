# Jarvis Audit — soft delete / createdBy / updatedBy / event log

Scope: phases 0–10 shipped code. Read-only review.

## Summary

The audit pillars are largely well-implemented. The Event model conforms to the spec, every domain mutation across accounts/transactions/transfers/categories/bills/budgets/attachments/loans emits a typed event inside the same `$transaction` as the state change, and partial unique indexes scoped on `deleted_at IS NULL` exist for the core tables. However, there are two material gaps: (1) `households.service.ts` uses a NON-transactional `recordEvent` for several mutations (orphan-on-rollback risk), and (2) there is no centralized event-type registry — types are passed as free strings at every emission site, with five separate `recordEvent` helpers duplicated across modules. A few schema-level audit columns are also missing on secondary tables.

## Findings

| # | Severity | Area | File / location | Finding |
|---|---|---|---|---|
| 1 | BLOCKER | Event log — atomicity | `apps/api/src/households/households.service.ts:43,81,315,327,377` (`this.recordEvent(...)` defined at line 440) | `recordEvent` runs `this.prisma.$executeRaw` OUTSIDE any `$transaction`. The preceding `household.create` / `household.update` / `householdInvite.create` / `householdInvite.updateMany` / invite-accept transaction commit independently. If event insert fails the domain mutation is already committed; if the mutation fails AFTER the `await` returns successfully the event still goes in (less likely), but more importantly there is NO atomic guarantee. Compare with `categories|accounts|transactions|bills|budgets|loans|transfers` which all use `prisma.$transaction(async (tx) => { ...; await recordEvent(tx, ...) })`. |
| 2 | BLOCKER | Event log — atomicity | `apps/api/src/me/me.service.ts:156` (`recordUserEvent`) called from `apps/api/src/me/me.controller.ts:94,101,123,143,152,173,194,216` | `recordUserEvent` is invoked AFTER the controller's mutation calls (e.g. update profile, change email, revoke session, update security/preferences) without a wrapping `$transaction`. Same orphan-event / lost-event risk as #1. The helper itself uses bare `prisma.$executeRaw`, not a `tx`. |
| 3 | MAJOR | Event types — no registry | `apps/api/src/{accounts,transactions,transfers,categories,bills,budgets,attachments,loans,households,me}/*.service.ts` | Event types are inline string literals (`'loan.created'`, `'bill.paid'`, `'household.invite_accepted'`, `'user.email_changed'`, etc.). Spec checklist: "Event types are stable, namespaced strings... from a single registry." There is no `events/registry.ts` or enum/const map; typos cannot be statically detected and downstream consumers (activity feed, notifications) cannot import a canonical list. |
| 4 | MAJOR | Event payloads — no Zod schema | same files as #3 | Spec checklist: "Event payload is structured and validated (Zod schema per event type)." Payloads are constructed as ad-hoc object literals; no per-type schema, no validation, no shared TS type. Risk of payload drift between emitter and consumer. |
| 5 | MAJOR | DRY / anti-fragility | `recordEvent` duplicated in `accounts.service.ts:521`, `transactions.service.ts:700`, `transfers.service.ts:374`, `categories.service.ts:381`, `budgets.service.ts:1104`, `bills.service.ts:1045`, `households.service.ts:440/445`, `me.service.ts:156` plus inline raw-SQL in `weekly-summaries/weekly-summary.scheduler.ts:85` and `bills/bill-scheduler.service.ts:145,160,299` | Eight near-identical `INSERT INTO events ...` raw-SQL blocks exist. A single `EventsService.recordEvent(tx, type, payload)` consuming a typed registry would consolidate them and eliminate variance (e.g. attachments imports `recordEvent` from bills — odd cross-module dependency). |
| 6 | MAJOR | Soft delete — schema | `apps/api/prisma/schema.prisma` `model BillPayment` (line 361) | Has `deletedAt` and `createdBy`, but no `updatedBy` and no `updatedAt`. The spec lists Bill (parent) explicitly; BillPayment is a core mutable child (undo flips `deletedAt`) and should track who undid it. |
| 7 | MAJOR | Soft delete — schema | `apps/api/prisma/schema.prisma` `model Notification` (line 255) | Has `deletedAt` (added in changeset 008) but no `createdBy` / `updatedBy`. Acceptable since notifications are system-generated, but the audit checklist applies — at minimum document the exemption. SUGGESTION-tier if deliberate. |
| 8 | MAJOR | Audit columns — schema | `apps/api/prisma/schema.prisma` `model LoanLumpSum` (line 539) | Child of Loan; has `createdAt/updatedAt` only. No `deletedAt`, no `createdBy`, no `updatedBy`. Loan lump sums are user-edited rows that affect amortization — they should carry audit columns and soft-delete (or be documented as hard-delete-on-loan-update, which the current code does: `tx.loanLumpSum.deleteMany({ where: { loanId: id, householdId } })` at `loans.service.ts:483`). Hard-delete of household-owned data is itself a MAJOR per the checklist. |
| 9 | MAJOR | Audit columns — schema | `apps/api/prisma/schema.prisma` `model Category` (line 142) | `createdBy` and `updatedBy` are nullable (`String?`). All other core tables (Account, Transaction, Transfer, Bill, Budget, Attachment, Loan) use `String` (NOT NULL). Acceptable only for system-default categories (`householdId IS NULL`); for household-scoped categories these should be NOT NULL. Backfill changeset is required if added now. |
| 10 | MAJOR | Soft-delete middleware coverage | `apps/api/src/prisma/prisma.service.ts` `SOFT_DELETE_MODELS` (line 49) vs `model BillPayment`, `model LoanLumpSum` | `BillPayment` HAS a `deletedAt` column in the schema (used by undo path) but is NOT listed in `SOFT_DELETE_MODELS`. Reads via `prisma.billPayment.findFirst` will therefore return soft-deleted rows by default. The bills service compensates explicitly (see `bills.service.ts:903` `if (target.deletedAt) throw ...`), but anywhere that doesn't compensate will leak deleted payments. |
| 11 | MAJOR | Soft-delete middleware — write ops | `apps/api/src/prisma/prisma.service.ts:140` (only patches `findMany/findFirst/findUnique`) | The middleware does NOT patch `update`, `updateMany`, `count`, `aggregate`, `groupBy`. Updates against soft-deleted rows are silently allowed (call sites must guard explicitly), and aggregate/count queries will include deleted rows. Many call sites do guard, but it's inconsistent. |
| 12 | MAJOR | Soft-delete middleware — fragility | `apps/api/src/prisma/prisma.service.ts:98-156` | Implementation monkey-patches delegate methods at boot. Comment admits "Prisma v7 removed `$use`... we apply via wrapper here." This is brittle: any future Prisma client regeneration or extension chain mutation will silently bypass the guards. There is no runtime invariant test. Consider migrating to `$extends({ query: { $allModels: { ... } } })` per current Prisma docs. |
| 13 | MAJOR | Restore path — explicitness | `apps/api/src/{loans,accounts,bills,budgets,categories,attachments,transactions,transfers}/*.service.ts` | Restore is implemented via dedicated methods (e.g. `restore()` on each service) which is correct per the checklist. PASS — included for completeness. |
| 14 | MAJOR | Hard delete of household-owned data | `apps/api/src/loans/loans.service.ts:483` `tx.loanLumpSum.deleteMany(...)` | Loan update path hard-deletes all `LoanLumpSum` rows and re-inserts. No event emitted for the deletes; no audit trail. Either (a) soft-delete the existing rows + add new ones, or (b) emit a `loan.lump_sums_replaced` event with before/after, or (c) document the justification. |
| 15 | MAJOR | Activity feed — read scoping | (no dedicated activity feed/events controller found in `apps/api/src`) | The Event table is written everywhere but there is no `events.controller.ts` exposing the activity feed. If/when added, ensure `householdId` is forced from auth context (cross-link `tenancy.md`). Currently no read endpoint exists, so the BLOCKER cited in the checklist is moot for now. |
| 16 | MAJOR | Notification dispatch coupling | `apps/api/src/notifications/notifications-dispatch.service.ts` | Dispatcher writes `notifications` rows directly inside the caller's `tx` and queues push/email post-commit. Spec says "Notification dispatch reads from the event stream (or in-process bus) — never duplicates the trigger logic." Currently each domain service decides when to call the dispatcher AND emits the event separately (see e.g. `bills.service.ts:824` recording `bill.paid` and the bill scheduler emitting both events and notifications in parallel). There is no event-bus subscription — the trigger logic is duplicated across the event emission and the dispatch call. Acceptable for v1 if intentional, but flag for a future phase. |
| 17 | MAJOR | createdBy / updatedBy auto-population | `apps/api/src/{accounts,bills,budgets,categories,loans,transactions,transfers,attachments}/*.service.ts` | Currently every service manually sets `createdBy: userId, updatedBy: userId` from the auth context inside service methods — there is no Prisma middleware or a single hook. This is fine and never reads from the request body (verified: no DTO accepts `createdBy`/`updatedBy` apart from `attachments.dto.ts:72` which is the RESPONSE DTO, not input). PASS, but a single middleware would be more robust than 30+ scattered assignments. |
| 18 | MINOR | Event append-only — DB-level guard | `db/liquibase/changelogs/*` | No database-level trigger or table-level grant prevents UPDATE/DELETE on `events`. Code-level there are no `event.update` / `event.delete` calls (verified by grep), but the spec says "append-only" — consider `REVOKE UPDATE, DELETE ON events FROM <app_role>` or a `BEFORE UPDATE/DELETE` trigger raising an exception. |
| 19 | MINOR | PII in event payloads | `apps/api/src/me/me.controller.ts:123` `'user.email_changed'` payload, `households.service.ts:315` `'household.invite_created'` payload `{ email, role }` | Both store the email address in the event payload. Email is already in `users` / `household_invites`, so this is not NEW PII, but it's now also in `events.payload` which lacks the deletion paths the source tables have. Verify retention policy. |
| 20 | MINOR | Event index | `apps/api/prisma/schema.prisma:315` only `@@index([householdId, createdAt(sort: Desc)])` | Activity feed by `type` (e.g. "show me all bill.* events") will table-scan. Consider `@@index([householdId, type, createdAt(sort: Desc)])` once read patterns solidify. |
| 21 | MINOR | `recordUserEvent` data-integrity hack | `apps/api/src/me/me.service.ts:163-171` | Comment: "Events table requires a non-null household_id. For user-scoped events lacking a household context, we pick any one the user belongs to so the row has a valid FK." This is a SCHEMA-MODEL mismatch: user-scoped events (`user.profile_updated`, `user.security_updated`) don't conceptually belong to a household. Either make `events.household_id` nullable, or introduce a separate `user_events` table, or accept the model. Currently emits to a "random" household which is misleading for analytics. |
| 22 | SUGGESTION | Notification mark-read | `apps/api/src/notifications/notifications.service.ts` | Mark-as-read mutates state but presumably emits no event (file does not import `recordEvent`). Likely intentional (read-receipts aren't activity-feed material) — confirm and document. |
| 23 | SUGGESTION | Transfer update events | `apps/api/src/transfers/transfers.service.ts` | Only emits `transfer.created` / `transfer.deleted` / `transfer.restored`. Confirm transfers are immutable post-create (no `update()` method observed) — if so, this is correct; flag if an update path is added later. |
| 24 | SUGGESTION | Bill scheduler actor | `apps/api/src/bills/bill-scheduler.service.ts:145,160,299` and `budgets.service.ts:811` | System-driven mutations pass `actorId = null` which is correct semantically. Consider a sentinel system user id (`SYSTEM_ACTOR_ID`) so the activity feed can render "System auto-paused this bill" without special-casing nulls everywhere. |
